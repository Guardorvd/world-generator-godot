# Правила проверок

## Таймауты и запреты (с 28.10.2026, жёстко)

- **Каждый запуск — только с таймаутом.** В каждом скрипте `tools/*.gd` и `tools/control/*.gd` первой строкой стоит сторожевой таймер `tools/watchdog.gd`: при превышении он печатает `ТАЙМАУТ: …` и завершает процесс с кодом 1. Кроме того, сам запуск из терминала или инструмента — с таймаутом не больше лимита скрипта + 30 с. Без таймаута и в фоне без таймаута не запускать.
- **Завис или вышел по таймауту — не перезапускать.** Не поднимать лимит, чтобы «прошло». Остановиться, написать пользователю, что и где зависло; причину искать по коду, а не повторным запуском.
- **По умолчанию запускается только изолированная сцена** изменённой системы. Любой другой тест (с генерацией мира, игровой сценой, `feel_test`, `check.gd`) — **запрещён без прямого повода**: изолированной сцены для изменения нет или она его не покрывает, и это видно из таблицы ниже. «Для надёжности» и «заодно» — не повод.
- Новый тестовый скрипт — сразу с `preload("res://tools/watchdog.gd").arm(self, <секунды>)` первой строкой `_init`/`_initialize`; лимит — реальное время с запасом.
- Устаревшие и сломанные скрипты (список в [docs/CONTROL.md](docs/CONTROL.md#устаревшие-и-сломанные)) не запускать без прямой просьбы пользователя.

## Главное правило (читать первым)

**С 11.4: где возможно, запускается только изолированная сцена** — маленькая сцена изменённой системы без генерации мира (например, `tools/road_look.gd` для полотна и обочин дорог). Она идёт секунды, её можно повторять при отладке и подборе чисел.

**Единая `tools/control/check.gd` на одном мире — только когда изолированной сцены для изменения нет или она его не покрывает** (генерация мира, хеши, загрузка, FPS тяжёлых систем, растительность в мире). Тогда она одна, один раз в конце; перед ней и после неё ничего не запускать: ни отдельных тестов, ни `selftest`, ни сверки с эталоном на нескольких мирах, ни замеров «до» и «после», ни `bench.gd`, ни повторов.

- Отдельный тест с генерацией — только если правка **прямо** затрагивает его систему, а ни изолированная сцена, ни `check.gd` её **не покрывают**. Тогда этот тест — **один**, **один раз**. Не два «для надёжности».
- Нет изолированной сцены для системы, которую часто правят, — лучше сделать её (по образцу `road_look.gd`), чем гонять генерацию.
- «Было» в изолированной сцене — прошлая версия кода, подставленная тем же запуском (у `road_look.gd` — `--shader <файл>`); в `check.gd` — прогон прошлой версии в `tools/control/runs`, его не пересъёмывать.
- Совпадение мира с прошлой версией проверяется по хешам из сводки `check.gd`, а не отдельным `selftest` или эталоном. Правка только шейдера или вида мир не меняет — хеши не нужны.
- Если кажется, что нужна ещё проверка, — не запускать её, а написать в отчёте, что не проверено. Пользователь решит сам.
- Только документы и правила — ничего не запускать.

Как запускать инструменты — [docs/CONTROL.md](docs/CONTROL.md).

## Общие правила

- Время проверок не больше времени разработки; на втором ПК мир 256 грузится больше минуты.
- Отладка и подбор чисел — в изолированной сцене, иначе на 1–2 снимках `check.gd` (`--views road --fps off`, свой `--world`). Полный набор видов и замер — один раз в конце.
- **Глубокая** (`check.gd --deep`, несколько сидов) — только по просьбе пользователя или когда единая показала падение FPS/загрузки больше шума (15 %) и нужна причина.
- FPS повторить один раз, только если разница больше шума. Короткие выборки (3 с) шумные: повтор — `--look 10 --road 10`.
- Процессы Godot с генерацией не запускать параллельно: они сбивают время и FPS.
- Скрипт с ошибкой разбора (`--script`) не запускается, но процесс может висеть или выйти с кодом 0 без вывода: перед запуском `godot --headless --check-only --script <файл>`.
- Перед `--script` запусками в сборке .NET — `dotnet build`; новый `class_name` — сначала `godot --headless --import`.
- В отчёте пользователю коротко: что проверено и что нет.

## Какая проверка для какого изменения

Не больше одной проверки с генерацией на изменение.

| Изменение | Проверка |
|---|---|
| Полотно дорог, обочины, шейдер рельефа у дорог | изолированная `road_look.gd` (было/стало через `--shader`, разбитые участки — `--shift x,z`); `check.gd` не нужен |
| Дороги и тропы стартового плана (`StageTrails`: связи, мосты, вторые пути, горные тропы), их скорость | изолированная `road_plan_test.gd` (`--compare` — тот же ли мир; `--stages` — время этапов, `--geo-check` — география); `check.gd` — только если пути меняются |
| Генерация мира, рельеф, реки, дороги, мосты, туннели | `check.gd`: хеши мира, снимки `road`/`valley` (`--world Ущелье` для мостов) |
| Местность за краем стартовой области; соседние области в игре (`RegionStream`) | `territory_test` (`-- --regions` — три области как в игре); путешествие, выгрузка, сохранение областей, их места и задания — `region_travel_test` |
| Подготовка соседних областей (`scripts/world/region_*.gd`): реки, вода, поселения, дороги, закрепление | изолированная `region_rivers_test.gd -- --neighbors`; заготовка области — `region_preparation_test.gd -- --gdscript` |
| Препятствия на дорогах (раскладка, ступени, кочки) | изолированная `road_obstacles_test.gd` (+ `road_look.gd -- --obstacles` для вида) |
| Подвеска, кочки полотна, ощущение езды без мира | изолированный `feel_test -- --downhill` (+ `road_look.gd` для вида кочек) |
| Модель седока, его анимации | `cyclist_animation_test -- --capture` |
| Велосипедные трассы, элементы, физика велосипеда на трассе | изолированная `trail_lab_test` (`-- --ui-only`, `-- --capture` по нужде); `feel_test` не нужен |
| Построитель линии по рельефу (`TrailRouter`), его кнопка в Trail Lab | изолированная `trail_route_test` (`-- --capture` по нужде) |
| Автоматический выбор места трассы (`TrailPicker`), кнопка «Найти трассу» | изолированная `trail_pick_test`; при правке этапов `TrailRouter` ещё `trail_route_test` |
| Автоматический выбор участка в области мира (`TrailScout`) | изолированная `trail_scout_test`; при правке `TrailPicker`/`TrailRouter` ещё их тесты |
| Велопарк стартовой области (`BikePark`: поиск пустой области, прокладка сети) | изолированная `bike_park_look.gd` (прокладка на синтетических холмах); в мире — один `bike_park_test.gd -- --seed Полынь-1312` (лимит 420 с) |
| Подключение трассы к миру (`StageTrailPlan`, запекание в `WorldLoader`, кэш плана) | `trail_world_test -- --scene --capture`: один запуск вместо `check.gd`; перед ним `trail_scout_test` |
| Доступ трассы к дорогам (`TrailAccess`, примыкания в `TrailRouter`, отбор пар в `TrailPicker`) | изолированная `trail_access_test`; при правке этапов ещё `trail_route_test` и `trail_pick_test` |
| Элементы на найденной трассе (`TrailFlow`, профиль `calm_flow`) | изолированная `trail_flow_test`; при правке `TrailComposer` ещё `trail_lab_test` |
| Сохранённая площадка мира в Trail Lab (`TrailSite`), сборка трассы на готовом полотне | изолированная `trail_site_test` (по файлу площадки); экспорт `trail_site_export` — только для новой площадки |
| Движение в мире, камера, проходы мостов и туннелей (то, чего нет в `trail_lab_test`) | `feel_test` (вместо `check.gd`, без FPS; лимит 5 мин) |
| Столкновения | `forest_collision_test` |
| Жизненный цикл мира, меню, память | `lifecycle_test -- --size 256 --worlds 3` |
| Графика, свет, небо, растительность, тяжёлые системы без своей сцены | `check.gd` с FPS (для света `--hours 7.5,19.1`) |
| Фара велосипеда (свет, луч) | изолированная `lamp_look.gd` (было/стало через `--lamp`) |
| Фотоаппарат: видоискатель, наведение на места, снимки | изолированная `photo_look.gd` |
| Задания, доска заданий, счётчик, сумка | изолированная `quest_look.gd` |
| Выносливость, геймпад (подписи кнопок, раскладка) | изолированная `stamina_test.gd` |
| Интерфейс игры (HUD, подсказки, дуга выносливости), выбор мира в меню | изолированная `hud_look.gd` |
| Интерфейс, настройки, звук | `settings_test` / `sound_check` или 1 снимок вместо `check.gd` |
| Только документы и правила | ничего не запускать |
