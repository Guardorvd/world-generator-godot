# Дорожная сеть V2: план реализации в экспериментальной ветке (21.11.2026)

Основа — план пользователя «Итоговый подробный план реализации» (фазы 0–4, ядро `Roads.Network` на C#), сверенный
с кодом ветки `Mechanics` (HEAD 7940315) и с планом [ROAD_NETWORK_PLAN_2026_11_19.md] (файл проекта; в репозитории не
лежит, не выполнен: стенд `road_plan_test.gd` всё ещё не разбирается, новых мер нет).

Правила проверок — [CLAUDE.md](../CLAUDE.md), [CONTROL.md](CONTROL.md) и инструкции проекта. Этот план им подчиняется:
отладка на изолированных стендах, один прогон стенда на сид на шаг, `check.gd` — один раз в самом конце.

## 1. Вердикт коротко

**Согласен с направлением:** ядро сети на C# за одной точкой входа; единый валидатор геометрии вместо разбросанных
проверок; граф сети как настоящий объект с правилами узлов; глобальный выбор петель вместо поштучных «сокращений» и
«обходов»; монотонное улучшение линии («оптимизатор не портит валидную дорогу»); флаг `V1/V2` и сравнение на тех же
сидах; синтетический стенд без генерации мира.

**Не согласен и меняю (подробно — раздел 3):**

1. **Без мостов в MVP нельзя.** Мосты через большие реки — красная линия пользователя, а без них поселения теряются
   (9.8: на Север-1234 из 11 мест оставалось 2, когда одна река без места для моста «съела» бюджет). Предложенная
   правка `StageLandmarks` под «сушу без мостов» меняет географию мест — это отдельная большая задача. **Решение:** V2
   сначала строит **всё, что после остова** (петли, ответвления, линии), а остов поселений с мостами и туннелями
   остаётся V1. Перенос остова — отдельная необязательная фаза, и даже там мосты строит существующий `_structures`.
2. **Долинные террасы (`dist_water` 3–14 клеток дешевле) убрать.** Это ровно полоса 12–56 м вдоль воды — дороги
   пойдут по берегам, против чего пользователь (17.11: «берега дешевле» уже отвергнуто). Береговые ответвления — только
   «к воде», не «вдоль», с пределом числа.
3. **Свой A* (K16) не писать в MVP.** `FastGrid.FindPath` уже на C#, с окном поиска (`SetWindow`), шириной прохода,
   штрафами поворота и галсов, закрыт эталоном `path_golden` (722 хеша). Углы «без дуги» лечатся на этапе линии, а не
   в поиске (память 15.11). K16 и серпантинный модуль — только если замер после фазы линии покажет нужду.
4. **Не дублировать арифметику.** `GroundAt/DepthAt` не копировать из `FastGrid.Water.cs` — вызывать её; проверку
   отрезка брать из `FastGrid.RoadSegment`, профиль 12 м — из правила `RoadLine.profile_ok` (`PROFILE_BASE = 3.0`).
   Не вводить новых порогов воды (в плане «`depth ≤ 0.3`» — такого правила в коде нет).
5. **Не переносить в C# то, что не тормозит и имеет одну копию:** `RoadSection.fit`, разметку `path_mask`
   (`Grid.stamp_path`), `road_id` (`Topology.section_id` — SHA-256 строки с `roundi`; копия на C# рискует разойтись в
   форматировании). Публикация V2 идёт через существующий `StageTrails._add_trail` — узлы, `Topology`, маска, «протоптанность»
   и записи получаются те же, что у V1. Порт — только по замеру.
6. **`RoadContract` — в конце, а не в фазе 0.** Пока V1 жив, вынос констант ничего не даёт, а внешних ссылок больше,
   чем семь модулей из плана: снаружи зовут и «приватные» функции (`_add_trail`, `_wet`, `_unsafe_fords`,
   `_clear_huts`, `_retain_connected_settlements`, `_count_failure`, `_route_surface` …, раздел 2).
7. **Матрица проверок фазы 3 сокращена до правил проекта.** `road_safety_test` — в списке устаревших; соседние области
   без дорог (`RegionRoads.NETWORK = false`), их тесты не нужны; `stress --verify-ride` проверяет `RideGround`, который
   V2 не трогает; `feel_test` — только если менялись мосты/туннели (не меняются).

Остальное (DeterministicRng, RideRoutes и звериные тропы на C#, серпантины, параллельный поиск) — после MVP и только
по замеру (раздел 9).

## 3. Корректировки и почему

### 3.1 Объём V2 по фазам (вместо «всё сразу, потом удалить V1»)

| Часть | V1 сейчас | V2 MVP (фазы 1–3) | Позже, по решению |
|---|---|---|---|
| Звериные тропы | `_animal_trails` | V1 | порт, если замер покажет >5 % этапа |
| Остов поселений, роли, мосты, туннели, `_retain_connected_settlements` | `_settlement_trails`, `_upgrade_roles`, `_structures` | **V1 без изменений** | фаза 5: V2 выбирает пары остова, строит их V1 (`_connect_settlement`) |
| Тропа между сетями через реку (`bridge_gap`) | первая ветка `_second_ways` | **V1**, тем же циклом, первой | — |
| Сокращения и обходы (`shortcut`, `alternative`) | `_second_ways` поштучно | **V2: петли по t-спаннеру** | — |
| Смотровые и горные тропы, берег | `view`, `_mountain_trails`, `shore` | **V2: единый планировщик ответвлений** | — |
| Линия по клеткам | `RoadLine` (GDScript) | V1 в фазе 2, **C# в фазе 3** (сначала только для путей V2) | для всех путей — по решению после замера |
| Публикация, узлы, `road_id`, маска, ширина | `_add_trail`, `Topology`, `Section.fit` | **V1** (общий конвейер) | порт только по замеру |
| Природные маршруты | `RideRoutes` + `FastGrid.Rides.cs` | V1 на сети V2 | порт — фаза 6 по замеру |

Так каждая фаза даёт сравнимый мир, мосты и поселения совпадают с V1 по отпечатку, а откат — один флаг.

### 3.2 Поиск в коридоре — существующий `FastGrid.FindPath`

C#-ядро создаёт свой экземпляр `FastGrid` (по одному на поток) и вызывает `Setup`, `SetCorridor/SetWorldCorridor`,
`SetWindow`, `FindPath(cost, s, t, heights, climb, maxGrade, links, useCorridor, maxCrossGrade)` напрямую, без
передачи через Godot. Окно — прямоугольник вокруг пути на грубом графе с запасом ±14 клеток (±56 м); при неудаче ±24;
затем грубое ребро помечается закрытым и путь перепланируется **один** раз; потом пара отбрасывается с причиной.
Эвристика `HCost = 0.6` остаётся (сознательный размен, 2.3/план 19.11): множители V2 к цене не опускают клетку ниже
текущего минимума `w.cost`, поэтому качество поиска не хуже V1.

### 3.3 Поле цены V2 — меньше множителей, без берега

Основа — `w.cost` (биомы, вода, край плана, «протоптанность» V1). V2 умножает его только для своих путей:

- **хребты/отроги** для горных ответвлений: TPI `Hσ − H3σ > 4 м` → ×0,82;
- **экотон** (кромка леса, доля леса 5×5 в [0,25; 0,75]) → ×0,9 — проверить эффект; 17.11 «лес дешевле» эффекта не дал;
- **меандр на равнине**: низкочастотное поле из **готового** шума мира (`w.noise_field`, без новых шумов),
  ×(1 ± 0,15), гаснет на склоне `smoothstep(0.06, 0.01, |∇Hσ|)`;
- **у берега озера/моря дороже** для ответвлений и петель: полоса 0–3 клетки ×1,5 (против «путей вдоль берега»);
  реки не трогаем (броды нужны).

Убрано: долинные террасы (раздел 1, п. 2). `Hσ` (σ = 3 кл, сепарабельный Гаусс, вода маскируется) нужен и для TPI, и
для меандра; считается один раз на этап.

### 3.4 Граф сети и правила узлов

`RoadGraph` в C# строится из уже опубликованной сети V1 (оси `w.trails` людей, узлы по правилу `junction_ends` метрик) и
принимает рёбра V2. Правила для **необязательных** путей (строго), из плана пользователя, сверенные с V1:

- узел не ближе 100 м к другому узлу того же уровня (`sep`), кроме общего съезда (3-лучевая развилка, как
  `RoadForks.FORK_GAP`);
- не больше 4 рёбер в узле; не ближе `EXIT_R` (140 м) к центру поселения, кроме общего выезда (`_exit_cost` V1);
- 0 двойных пересечений с одним ребром; не идти параллельно сети дольше `PARALLEL_RUN` (60 м) — правило V1;
- угол примыкания 35–90° (мягко, через линию).

Ослабление Tier 2 для остова не нужно в MVP — остов строит V1. Контракция узлов степени 2 и слияние узлов < 30 м — только
внутри графа V2 (решения), опубликованные записи остаются участками `w.trails`, как сейчас.

### 3.5 Петли: t-спаннер вместо `SHORTCUT` и `alternative`

1. Пары — соседи по Габриэлю (как сейчас), без мест роли `remote` (`_single_access`).
2. `D_geo(u,v)` — Дейкстра на грубом графе (вода — только броды; через большую реку пары нет — это работа
   `bridge_gap` V1). `D_net(u,v)` — по готовой сети (`RoadGraph`).
3. Кандидаты с `D_net / D_geo > 1.65`, по убыванию отношения; лимит петель `μ ≤ ceil(0.35 · N)`.
4. Кандидат маршрутизируется в коридоре; принимается, если после добавления отношение для пары ≤ 1,25, правила узлов
   выполнены, отход от существующей связи дальше 60 м на 40 % длины (не дублёр), длина ≤ 2 длин старого пути.
5. После принятия `D_net` пересчитывается (сеть маленькая — дёшево).

### 3.6 Ответвления: горы, смотровые точки, берег

Один планировщик целей: вершины `w.peaks` (горные тропы), холмы над перегоном (`VIEW_RISE 15 м`, `VIEW_GAP 240 м`),
вода (`shore`). Цели не ближе `VIEW_GAP` друг к другу и смотровая не ближе `VIEW_GAP` к вершине (у неё своя тропа).
Берег: не больше `max(2, N/4)`, путь отклоняется, если больше 25 % клеток (без последних 4) ближе 3 клеток к воде
(план 19.11, шаг 1.1). Вход на перегоне — дальше `EXIT_R` от поселения, точка съезда — по правилам 3.4.

### 3.7 Линия на C# (фаза 3) — проверенный путь, потом улучшение

1. Сначала **порт `RoadLine` 1:1** для путей V2 (срезание лесенки, хорда/дуга, `profile_ok` по 12 м, поблажка
   `line_relax`) со сверкой на стенде против GDScript (одинаковые точки до 1e-6 клетки). Это даёт ускорение без смены вида.
2. Затем **монотонное сглаживание** поверх: несколько итераций сдвига точки к среднему соседей (Лаплас) с удержанием в
   коридоре и отталкиванием от чужих рёбер; каждый сдвиг проверяется валидатором на окне `[i−3, i+3]`, при нарушении
   шаг ×0,5 до 3 раз, иначе точка стоит. Концы закреплены точно в узлах. Δ⁴/клотоиды и Катмулл–Ром — только если
   `corners`/`kinks` не падают.
3. Плотность точек — как у V1 (не 2 м): от неё зависят `RoadRefinement`, кэш и время `_add_trail`.
4. Разворот > 105°: апекс выносится наружу до радиуса `half + REACH(3,0 м) + 1 м`, иначе точка остаётся (защита `FitSafe`).

### 3.8 Флаг и кэш

`StageTrails.network_v2 := false` (статическая, как `routing_overrides`). При `true` к ключу слоя `places` добавляется
`|net=v2.<RoadNetworkV2.VERSION>` (`WorldCache._road_layer_suffixes`), иначе игра с флагом загрузит мир V1 из кэша и
наоборот. `SCHEMA_TRAILS_VERSION` поднимается только при переключении умолчания (фаза 7).

## 5. Общие правила проверок этой работы

  `w.road_rides`, `w.bridges/tunnels` (не изменились), `generation_profile` (все ключи стенда `KEYS` и `network_v2`),
  `WorldGenerationState` — заполняются общим конвейером; V2 не пишет в мир в обход `_add_trail`.
- **Одна правда.** Каждое правило (вода, профиль, крен, броды, выезд, параллельность) существует в одном месте;
  если в C# повторена формула V1 — есть сверка на стенде и ссылка на источник.
- **Детерминизм.** Нет случайности и зависимости от порядка словарей; сортировки с полным ключом; повтор на стенде.
- **Память и время.** Поля `W·H` — один раз; на ребро — окно; GC-выделений в горячем цикле нет; время частей — в
  `generation_profile.network_v2`; сравнение только с базой фазы 0.
- **Ошибки громко.** Нет сборки C#, неверный вход, нарушение инварианта — `push_error` с текстом; молчаливого отката на V1 нет.
- **Отчёт пользователю** после фазы: что проверено (стенды, сиды), что нет, картинки V1/V2, таблица раздела 10.

## 9. Что сознательно не делается (и когда может понадобиться)

- Свой A* K16 и серпантинный решатель `(c, θ8, q)` — только если после фазы 3 на Ущелье горные тропы упираются в
  `line_grade_fallbacks`/`hairpins`; отдельным решением.
- Порт `RoadSection.fit`, разметки маски, `road_id` в C# — нет выигрыша, есть риск расхождения.
- Новое размещение поселений «без мостов» — не нужно при остове V1.
- Долинные террасы и любое удешевление берега.
- Изменение `HCost`, штрафа уклона, `TRAIL/MOUNTAIN/ROAD_GRADE`, `FitSafe`, `RbJoin`, `RoadBedRefine`, `CROSS_RUN`.
- Соседние области (`RegionStream`, `region_*`) и Trail Lab.
- Параллельные дороги как цель — нет; параллельность только как запрет.
